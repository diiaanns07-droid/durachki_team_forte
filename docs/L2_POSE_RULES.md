# Профиль pose_rules: люди + скелеты + предметы + треки + зоны + правила по времени

Отчёт L2 о профиле анализа без обязательной VLM. Цифры — исследовательская оценка на 42 обучающих видео
(40 уникальных по SHA-256), не независимый тест. Подробные результаты по видео остаются локально (`runs/`, вне git).

## 1. Цепочка наблюдений

```
кадр с реальным PTS (ml.ingest, переменный fps)
  → люди и предметы (ml.detect: RT-DETRv2 + OWLv2)          score модели, источник
  → track_id (ml.track: ByteTrack + склейка, авто-зоны)      без дорисовки боксов (fill_gaps_s = 0)
  → суставы COCO-17 (ml.pose: RTMPose ONNX, кроп по треку)    поза привязана к track_id по bbox, не по порядку
  → зоны и взаимодействия (ml.seqrules)                      observed / absent / unknown на каждом шаге
  → эпизоды во времени (допуск пропусков, слияние повторов)  t_start / t_end / t_anchor (= начало)
  → события контракта (source = rules_seq) → ml.fusion → ответ API по схеме ТЗ
  → наблюдения для UI: data/jobs/<id>/observations.json → GET /jobs/{id}/observations
```

Три состояния:
- **observed** — есть детекция модели (её score и происхождение сохраняются);
- **absent** — кадр обработан, нужные суставы видны, искомого рядом нет;
- **unknown** — кадр не обработан, человек не детектирован, суставы ниже порога видимости.

Потеря детекции человека не означает, что он ушёл. Необработанный кадр не считается «отсутствием».

## 2. Запуск

```bash
python tools/l2/run_profile.py pose_rules run data/raw/X-15.mov --out runs/l2/pose_rules/X-15.json
python tools/l2/run_profile.py pose_rules batch data/raw --out runs/l2/pose_rules/preds --deadline 270
python -m eval.metrics --preds runs/l2/pose_rules/preds --labels data/labels.csv --out runs/l2/pose_rules/metrics.json
```

Сервер: `SENTINEL_PROFILE=pose_rules` в `deploy/.env` (или в окружении), затем `deploy\windows\start.ps1`.
Профиль — три файла без секретов:
- `deploy/profiles/pose_rules.env` — переменные окружения модулей;
- `backend/pipeline/profiles/pose_rules.yaml` — стадии, обязательные стадии, бюджеты;
- `ml/pose/presets/pose_rules.yaml` — бэкенд позы и отбор людей.

Вариант с ограниченной проверкой кандидатов VLM — `pose_rules_vlm`. После загрузки весов всё работает офлайн.

Выбран **RTMPose**: в 5 раз быстрее при той же доступности запястий, на которых держится правило А, и выше
доля кропов со скелетом. MediaPipe подключён как переключаемый бэкенд (`SENTINEL_POSE_BACKEND=mediapipe`,
`running_mode: video`). В нём: отдельный поток на track_id, монотонные метки времени из PTS, поза выбирается
по bbox трека (порядок поз модели — не идентичность), лимит потоков с вытеснением. Влияние MediaPipe на
события на всех 42 видео не измерялось.

## 4. Правила (ml/seqrules, пороги — `ml/seqrules/config.yaml`; это технические параметры, не нормы)

| Правило | Условия | Мин. видимость | Длительность / пропуски | Отмена / неопределённость | Тип каталога |
|---|---|---|---|---|---|
| А. Телефон | телефон (score ≥ 0,30) у запястья (≤ 0,25 высоты человека) или головы конкретного трека; предмет перемещается или у головы; человек — сотрудник или на рабочем месте | запястье/голова ≥ 0,30 | ≥ 1,5 с и ≥ 4 кадров; пропуски ≤ 1,0 с | лежит неподвижно рядом с рукой; контраст OWLv2 на кропе: «другой предмет стола» (стационарный телефон, калькулятор, терминал); не на рабочем месте | V05 (кандидат нарушения) |
| Б. Сейф без присмотра | рабочая зона пуста ≥ 3 с после наблюдаемого выхода сотрудника; дверца сейфа распознана открытой ≥ 2 проверок подряд | кадры обработаны; проверки по кадрам | проверки каждые 2 с, не больше 4 на интервал | пропал внутри зоны (потеря ≠ уход); вышел, но виден рядом; зона пуста с начала; сейф закрыт / не определён / не проверен | V03 (кандидат нарушения) |

| Рука — деньги (выкл.) | центр «денег» у запястья | запястье ≥ 0,30 | ≥ 0,6 с | — | только наблюдение, без вывода о хищении |

Таймкод события — начало эпизода (`anchor_policy: onset`). Повторы одного правила одного человека ближе 2 с
сливаются. Для телефона слияние работает и при смене ID трека на том же месте. Решения не зависят от имени
файла, порядка роликов и их длительности; синтетический тест проверяет это перестановкой треков и детекций
и сменой имени файла.

## 5. Интерфейс

Оверлеи поверх видимой области кадра:
- скелеты с номером трека и ролью;
- рамки предметов со score;
- зоны, рабочая зона выделена;
- сустав, к которому привязан предмет;
- проверки сейфа;
- метка «неизвестно» или «не видно рядом», если в этот момент наблюдения не было.

Слои включаются и выключаются. Показывается только то, на чём основаны события: выбранный эпизод или все
эпизоды-основания. Выбор эпизода общий для шкалы, навигатора, боковой панели, карточек и оверлея.

Карточка «Наблюдения правил» показывает статус каждого правила (проверено, неприменимо с причиной, ошибка)
и состав выбранного эпизода: сколько кадров наблюдалось, сколько неизвестно, проверки сейфа. Стартовая
сцена не изменена. JSON по схеме ТЗ не изменён, наблюдения отдаются отдельным эндпоинтом.

## 6. Исследовательская оценка (42 файла → 40 уникальных по SHA-256)

**Покрытие.** Обработано 42 из 42 видео: ошибок 0, необработанных 0, неполных 0. Дубликаты сгруппированы
по SHA. Конфликт X-4/X-47 (одна запись, разные таймкоды) не разрешался: метки совпадают, поэтому группа
входит в бинарные метрики, но не входит в основную локализацию.

**Вердикты** (`eval.metrics`; failed/partial на позитиве = FN, на негативе ≠ TN):

| Профиль | TP | FP | TN | FN | Точность | Полнота | F1 | Доля верных | Специфичность |
|---|---|---|---|---|---|---|---|---|---|
| прошлый (VLM по кадрам, exp4) | 12 | 10 | 9 | 9 | 0,55 | 0,57 | 0,56 | 0,53 | 0,47 |
| **pose_rules** | 6 | 7 | 12 | 15 | 0,46 | 0,29 | 0,35 | 0,45 | 0,63 |
| объединение двух («или») | 13 | 14 | 5 | 8 | 0,48 | 0,62 | 0,54 | 0,45 | — |

**Локализация** (только однозначные события, окно сопоставления 5 с): pose_rules — 2 из 20 событий, медиана
|Δt| = 2,6 с; прошлый профиль — 7 из 20, медиана 1,4 с.

**Классификация типов: N/A.** Типы, подтверждённые человеком, отсутствуют (`labels_types.csv`: confirmed=0
во всех строках). Предложения VLM и псевдоразметка эталоном не считаются.

**Что сработало по правилам** (все 42 видео):
- **А (телефон):** 24 эпизода стали событиями; 10 отклонены контрастной проверкой («другой предмет стола»),
  19 — неподвижный предмет рядом с рукой, 203 — короче порога. Контрастных проверок 68: мобильный 22,
  не мобильный 18, неоднозначно 28.
- **Б (сейф):** 0 эпизодов. Рабочая зона ни в одном видео не пустела на 3 с и дольше: кассир виден в
  90–100 % кадров с уверенным скелетом (медиана score плеч 0,74). До проверки сейфа правило не дошло.
- **В (вход в зону):** 6 наблюдений; это подсказки, в вердикт они не входят.

Вывод: новый профиль объяснимее и реже даёт ложные срабатывания, но пропускает больше. На этих видео он
надёжно видит только телефон у руки. Нарушения с сейфом и деньгами упираются в распознавание предметов
(см. таблицу ниже), а не в правила.

## 9. Что не работает и что нужно проверить человеку

- **Правило Б (сейф).** На этих видео не срабатывает: сейф не детектируется, рабочая зона не пустеет.
  Нужны размеченные кадры «сейф открыт / закрыт» и дообучение детектора.
- **Деньги и инкассаторская сумка.** Слабый сигнал OWLv2 (9/40 и 5/40 видео). Правило «рука — деньги»
  выключено, пока детектор не подтверждён разметкой.
- **Телефон.** Детектор срабатывает на предметы стола во всех видео. Связь с запястьем, движение и контраст
  на кропе отсекают часть ложных, но 7 FP остаются. Кадры событий V05 стоит просмотреть человеку.
- **Роли.** Роль «сотрудник» — эвристика трекинга. При ошибке роли правило А может пропустить человека не на
  рабочем месте, а правило В — назвать сотрудника посетителем. Поэтому В — только наблюдение.
- **Разметка типов.** Подтверждённых человеком типов нет, классификация не оценивалась. Нужна разметка типов
  с `confirmed=1`.
- **Кандидаты на разметку.** `runs/l2/objects/labeling_candidates.csv` (локально) — для ручной проверки, не эталон.
- **Тесты.** `deploy/tests/test_offline.py`: 2 теста падают из-за кодировки консоли (cp1251, символ «≠»).
  Падение было и до изменений L2.

## 10. Эксперимент: место хранения, найденное по рукам (два прохода, один фактор)

Идея: сейф не распознаётся по виду, но камера неподвижна, и кассир тянется к нему руками.

- **Проход 1.** По скелету сотрудника ищем эпизоды, где рука вытянута за пределы стола и зоны клиента.
  Порог — 2 ширины плеч и на 0,6 дальше обычного положения рук этого человека; поза дольше 8 с — не движение.
  Цели вытягиваний группируются в места.
- **Проход 2.** После ухода руки место проверяется на увеличенной вырезке: OWLv2 «открыто или закрыто»
  и сравнение вида места до касания и после.
- **Событие** (V03, кандидат): ≥ 2 проверки подряд «открыто», рук у места нет, вид не вернулся к исходному.
  Что это за место (сейф, ящик, шкаф), система не утверждает.

Профиль `pose_rules_storage` = `pose_rules` + это правило (`eval/configs/l2/seqrules_storage.yaml`). По умолчанию
правило выключено.

| Профиль (диагностика на 40 знакомых группах) | TP | FP | TN | FN | Доля верных | Сбалансированная | Точность | Полнота |
|---|---|---|---|---|---|---|---|---|
| старый VLM (контроль) | 12 | 10 | 9 | 9 | 0,525 | 0,523 | 0,55 | 0,57 |
| pose_rules | 6 | 7 | 12 | 15 | 0,45 | 0,459 | 0,46 | 0,29 |
| pose_rules + место хранения | 7 | 7 | 12 | 14 | 0,475 | 0,482 | 0,50 | 0,33 |

pose_rules → + место хранения: исправлено 1, испорчено 0. Правило дало 2 события на 42 видео.

Ограничение — распознавание состояния места. Из 59 проверок 25 закрыты рукой, 24 неоднозначны, 10 «открыто»,
«закрыто» — ни одной. Разведка до реализации: вытягивание руки к месту вне стола попадает в окно ±5 с вокруг
размеченного нарушения в 48 % видео с нарушением против 27 % случайных окон видео без нарушения. Сигнал
о моменте есть, но для вердикта нужно надёжное «открыто / закрыто».

## 11. Разбор ошибок и исправление (диагностика на 40 знакомых SHA-группах, не независимый тест)

**Фиксация.** Контроль — старый профиль VLM по кадрам (exp4: `runs/l2/exp4.yaml` + `eval/configs/l2/vlm_states_v3.yaml`).
Разбираемый — `pose_rules`. Оба на одном коде детекции: ключи кэша детекции совпадают во всех 42 видео, частота
кадров 5,0, число кадров одинаковое. `tools/l2/freeze_results.py` проверяет:

- **Видео ↔ метки:** sha256 в ответах совпадает с манифестом в 42 из 42.
- **Кэш:** режим `read_write` — используются только записи с совпавшим ключом, устаревших нет.
- **Ответы:** все 42 `done` и `complete`; «нет нарушения» при неполном анализе — 0; таймаутов стадий 0.
- **Ошибка запуска в контроле:** необязательная стадия `temporal` упала во всех 42 прогонах, контроль получен
  без временной модели.
- **Параметр запуска:** ниже дедлайна ≈ 250 с нарезка кадров реже. X-15 даёт 94 кадра при 240 с и 105 при 270 с,
  а `meta.sample_fps` остаётся 5,0. Сравнивать профили нужно при одинаковом `--deadline` (сервер — 270 с).

**Причины 15 пропусков `pose_rules`** (`tools/l2/error_causes.py`, только по трассировкам):

- **Реализованные правила в момент нарушения ничего специфичного не видели — 14 из 15.** Короткие эпизоды
  телефона и «появился уже в зоне» в окне ±5 с встречаются не чаще фона: 0,47 против 0,59 и 0,60 против 0,43
  в случайных окнах видео без нарушения. Причиной они не засчитываются.
- **Событие входа в зону ушло в подсказки — 1.** Так задумано: вход в зону — наблюдение.
- **Не подтверждаются ни для одного пропуска:** «момент вне обработанных кадров», «нет людей или суставов»,
  «пропуск по бюджету», «ошибка правила».
- **Типы нарушений не подтверждены человеком,** поэтому «тип не поддерживается» доказать нельзя. Страницы для
  человека: `cache/types_review/index.html` (типы) и `cache/error_review/preds/index.html` (FN/FP), обе локальные.

**Охват.** В `pose_rules` выключены сцена, правила A09 и путь VLM по кадрам; вход в зону — только наблюдение;
«рука — деньги» выключено.

- 7 из 15 пропусков поймал выключенный путь VLM старого профиля; 11 из 13 подтверждённых кандидатов там от VLM.
- Точность этого пути по типам (в скольких группах тип вошёл в ответ): V01 — 6 с нарушением / 4 без,
  V05 — 7 / 8, V04 — 1 / 3.
- Главная доказанная причина — **пробел в охвате**: нет пути распознавания для того, что происходит в момент
  нарушения.

**Отвергнутые варианты** (оценка по трассировкам):
